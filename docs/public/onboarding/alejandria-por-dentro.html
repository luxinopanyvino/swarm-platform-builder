1 · El proyecto

Qué es y qué produce

swarm-platform-builder es una plataforma para definir y ejecutar equipos de agentes de IA. Cada agente tiene un perfil, unas capacidades (buscar en documentos, llamar a un modelo, dar formato…) y un lugar en un grafo. El grafo no está escrito en Python: es un dato, un template.yaml por proyecto.

El proyecto de referencia es AlejandrIA Magazine: cinco agentes que investigan, redactan, revisan, formatean y publican artículos científicos. Es a la vez producto y banco de pruebas: lo que la plataforma promete (aislamiento entre proyectos, trazabilidad, evaluación) se demuestra sobre él.

Dos sentidos de «agente» conviven en el repo

Agentes de producto: los del pipeline, perfiles en base de datos y en *.agent.md. Son la funcionalidad.
Agentes de desarrollo: .claude/agents/ (task-runner, sdd-sync), que implementan y sincronizan el backlog. Son herramientas del repo.

4 · Cómo trabajar

Del issue a la PR, y del plan a la página

Tres cosas que vas a hacer a menudo. Todos los comandos se lanzan desde la raíz del repositorio; los que empiezan por / se escriben dentro de Claude Code.

Antes de la primera vez

  1. Instala Claude Code (la CLI claude o la extensión de VS Code) y GitHub CLI.
  2. Autentica gh con permisos de proyecto. Si acabas de instalarlo, cierra y abre VS Code para que la terminal lo encuentre.
    gh auth login --scopes project
  3. Comprueba que ves los issues:
    gh issue view 337 -R luxinopanyvino/swarm-platform-builder

Ejecutarla con la skill /resolve-task

  1. Elige una tarea lista para empezar en el diagrama y apunta su número de issue (la ficha lo trae).
  2. Abre Claude Code en la raíz del repo:
    claude
  3. Escribe la skill con el número. Puedes pasar varios, y se resuelven en orden:
    /resolve-task 337
  4. O, sin abrir la sesión interactiva (en Git Bash):
    bash scripts/run-task.sh 337

Qué hace por dentro

  1. Lee el issue: criterios, dependencias («Bloqueada por: #N»), área y severidad.
  2. Comprueba que todas las dependencias estén cerradas. Si alguna sigue abierta, se detiene y lo avisa: no implementa tareas bloqueadas.
  3. Crea una rama con prefijo desde develop y lee el código implicado.
  4. Implementa y ejecuta los tests. Si fallan, no sigue.
  5. Escribe la bitácora en docs/bitacora/tarea-N.md.
  6. Sube la rama y abre la PR contra develop con Closes #N. No mergea ni cierra issues.

Y después, tú

  • Revisa el diff como si lo hubiera escrito otra persona: es tu PR.
  • Comprueba que la CI está en verde y que cada criterio de la ficha se cumple.
  • Pide revisión; si la ficha lleva R, a alguien con experiencia.
  • Cuando se mergee, el issue se cierra solo y las tareas que dependían de él quedan listas. Regenera esta página.

Una tarea implementada pero con el issue abierto sigue bloqueando a las que dependen de ella: /resolve-task se detendrá. Ciérrala por el flujo (PR con su bitácora) antes de seguir.

Nunca crees issues a mano. El tablero se genera desde las specs: un issue sin su marcador oculto (<!-- sdd:task:T16.2 -->) queda «no gestionado», y uno duplicado bloquea la sincronización.

Una tarea nueva en una épica que ya existe

  1. Crea una rama docs/ y abre la spec de la épica (la ficha de cualquier tarea de la épica enlaza su spec).
  2. Si la tarea necesita un criterio que no existe, añádelo en la sección 3 como - [ ] **AC8** — *Given* …, *When* …, *Then* …
  3. Añádela al bloque sdd-sync de la sección 8: 
      - id: T16.7
    title: "Qué hay que hacer, en una frase"
    sev: medium            # high · medium · low
    depends_on: [T16.5]    # ids de tareas; [] si ninguna
    acceptance: [AC8]
  4. Valida las specs:
    python scripts/validate_specs.py
  5. PR contra develop. Cuando esté mergeada, en Claude Code, primero simula y luego aplica:
    /sdd-sync
    /sdd-sync --apply
  6. Opcional pero recomendable: su ficha en docs/onboarding/tareas.yaml (alcance, archivos, «ojo con», rama) y su sitio en el reparto. Regenera la página.

Una épica nueva

  1. Crea la spec con la skill de Spec Kit. Nace en Draft con su bloque sdd-sync:
    /speckit-specify "Descripción de la necesidad"
  2. Madúrala: preguntas a lo que quedó ambiguo, checklist de calidad de requisitos y análisis de consistencia con su ADR y sus tareas:
    /speckit-clarify SPEC-032
    /speckit-checklist SPEC-032 seguridad
    /speckit-analyze SPEC-032
  3. Cambia su Estado a Ready. Las specs en Draft no generan issues.
  4. Valida, abre la PR docs/ y, tras el merge, /sdd-sync y /sdd-sync --apply.
  5. Cada épica va a su tablero: E14 en adelante al roadmap; E1–E13, al backlog antiguo.
  6. Añade su nombre corto en epicas de tareas.yaml y regenera la página.

El número de spec y de épica es el siguiente libre. /speckit-specify lo propone, y la validación de specs falla si dos épicas se pisan.

Regenerarla

  1. Desde la raíz del repo, con gh autenticado (lee el estado de cada issue):
    python scripts/build_onboarding.py
  2. Sin red o sin gh, usa la última copia guardada del estado:
    python scripts/build_onboarding.py --sin-github
  3. Ábrela en el navegador: docs/public/onboarding/alejandria-por-dentro.html. También la sirve la web de documentación:
    luegocd docs && npm run dev
    y entra en http://localhost:5174/onboarding/alejandria-por-dentro.html
  4. Guarda el cambio en una rama docs/ con su PR, como cualquier otro.

Cuándo regenerarla

  • Después de /sdd-sync --apply (tareas o épicas nuevas).
  • Después de mergear PRs que cierran tareas (cambian las listas para empezar).
  • Al cambiar el reparto, una ficha o la arquitectura.

Definition of Done común

  • Cumple todos los criterios de aceptación de la tarea.
  • Tests automatizados que cubren el cambio, en verde en CI.
  • Sin secretos en el diff; dependencias nuevas escaneadas.
  • Documentación, spec o ADR actualizados si el cambio los afecta.
  • Si toca agentes, prompts o el dispatcher: el gate EDD pasa, o la regresión se explica en la misma PR.
  • Revisada y aprobada. Nadie mergea su propia PR ni cierra issues a mano.
